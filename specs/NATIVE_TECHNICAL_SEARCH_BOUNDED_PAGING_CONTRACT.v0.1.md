# HullQ — Native Technical Search Bounded Retrieval and Continuation Contract

**Version:** 0.1  
**Status:** PROPOSED for independent SLICE-0096 readiness review; not implemented, not an accepted public API version  
**Owner capability selection:** 2026-10-29 — source-backed, scalable, bounded Sail+Power technical Search retrieval, ahead of M1a cards/filters/navigation.  
**Underlying truth:** `specs/SEARCH_QUERY_SEMANTICS.v0.1.md`, existing Sail/Power criteria/FieldResolution/claim contracts and accepted OQ-018 public Search canonical identity. This contract **does not** create or revise a Search criterion.

## 1. One behavior: bounded, honestly complete-or-partial Search retrieval

A public Sail or Power technical Search is an evaluation over real, currently eligible NativeListings. A client can ask for a bounded page of `CONFIRMED_MATCH` results, safely continue through remaining candidates and tell whether evaluation is **COMPLETE** or **PARTIAL**. There must be **no unbounded ACTIVE-candidate enumeration**, no unbounded match-array materialization and no per-request silent fallback to the previous whole-inventory evaluator on a publicly reachable path.

**Critical distinction:** The available candidate read is not equivalent to the confirmed-match result set. A SQL `LIMIT` on raw ACTIVE candidates *without a continuation that covers the rest* is not correct Search pagination. Correctness demands either a qualified/index-backed match-ordered read whose equivalence is proven, or a bounded candidate scan with an explicit, truthful continuation cursor. Under a sparse search, a bounded scan may return **zero matches with PARTIAL**; the UI MUST say the search is incomplete and allow continuation. It must NEVER present that as “no matching boats”.

For a static database and fixed query, exhaustive traversal of all continuation pages must recover the identical eligible confirmed-match identity set and evidence source classification as the trusted pre-0096 evaluator, with no missing, duplicated or invented positive result. **Cursor progress is measured against the last candidate identity actually evaluated**, not the last match emitted: a no-match PARTIAL page still advances deterministically. Look-ahead or equivalent bounded exhaustion proof is required before announcing COMPLETE when the final batch happens to fill the page exactly. Non-match and insufficient data must not be promoted into confirmed matches to improve paging.

## 2. Transport/API and canonical Search identity

- All five Sail and Power buyer locales, direct technical Search routes and currently used FastAPI public Search endpoints must have a **bounded default**. No unbounded legacy public URL or API route may remain available merely for backward compatibility. Implementer MUST inventory the existing Sail pure-draft versus mixed-query and Power drive-only versus count/mixed route/DTO/client variants before selecting the smallest compatible migration strategy. A versioned page DTO may be introduced when the existing full-result counts cannot retain their original truth.
- Proposed user-facing page size **20** confirmed matches by default, hard ceiling **50**. These values are proposed transport/resource limits subject to readiness reviewer checks, not newly accepted marketplace pricing/product claims. A server-side bounded candidate-evaluation budget is separately configured and test-asserted; a page-size bound alone never proves bounded work.
- A `page_after` opaque continuation token is **navigation state**, not a technical Search criterion. If a `page_size` parameter is exposed, it is a bounded presentation preference, not a new hard technical criterion. Neither is included in the **canonical semantic Search identity**. This is an explicit, scoped OQ-018 parameter admission: all other unknown/duplicate/unrecognized keys remain fail-closed; category/locale, active requirement canonicalization, query key ordering, nonindex/search robots and canonical-link semantics remain valid. Frontend must show active technical constraints unchanged on later pages, and current page traversal must not rewrite saved search identity.
- The API must return typed **page-local** result arrays, truthful `page_size`, `evaluation_state = COMPLETE | PARTIAL`, and optional `next_cursor` only where continuation is genuinely possible. **A PARTIAL response MUST have a valid next_cursor; a COMPLETE response MUST NOT have one**; no cursor loop, duplicate page or non-advancing empty PARTIAL is valid. No global match/nonmatch/insufficient count unless accurately and boundedly established. Existing count fields cannot silently change meaning; if a new versioned response envelope is necessary, update Python serializers, web TypeScript validators, SSR state and tests in the **same** reviewed vertical change. A 200 response with missing, inconsistent or contradictory paging fields fails closed, never silently becomes “0 matches”.
- A cursor is bounded-length, opaque to clients, request-bound (category, active canonical technical requirement, relevant page-size/order state and serialization version), integrity protected or equivalently unforgeable, and expiration/invalid-version safe. **A navigation-only parameter without any active technical requirement is invalid (no paginated BASE query).** Duplicate, empty, malformed and noncanonical page-size/cursor keys must fail closed. If a request carries a cursor and noncanonical technical spellings/order, reject instead of issuing a 308 redirect that accidentally discards or rebinds the cursor; without cursor, retain the accepted existing 308 canonical behavior. No account/Organization ID, secret, raw claim source, private row data or unrestricted SQL is embedded. Query change, locale/category cross-use, tampering and cursor expiration must fail visibly (e.g. HTTP 400/409 controlled error) without returning a seemingly successful partial/complete page. If the canonical public URL excludes page state, document/shareable query URLs still work and `rel=canonical` points to the criterion-only identity.
- Keyset/seek order is **one monotonically increasing global NativeListing identity across both source classes**, not two independently paginated planes concatenated or restarted on each page; default order remains non-commercial and deterministic. The two mutually exclusive candidate planes must be covered in one traversal contract without both class duplication and unsafe candidate skips. A newly added/removed BoatDesignRef may switch an item between planes between HTTP requests; monotonic global identity and fresh classification must prevent reappearance or stale proof, while clearly documenting that dynamic populations cannot promise immutable snapshot coverage. Paged return of publisher-claim-only and design-linked successes may remain separate presentation sections provided their joined page coverage and source discrimination are exact.

## 3. Database, bounded cost and consistency

- First collect retained **real PostgreSQL 18** baselines for 0/40/200 and a qualified larger synthetic stress cohort where feasible; preserve mixed Sail/Power, category-negative, D29-ineligible, design-linked, design-unresolved, conflicting and sparse/zero-match cases. Report statement counts, `EXPLAIN (ANALYZE, BUFFERS)`, page/complete-traversal latency measurements (repeat runs; local versus hosted clearly labeled), memory/candidate counts and browser SSR request behavior. Old 0093/0094 figures are historical evidence, NOT new-run proof.
- Choose the least-complex provably correct bounded strategy after profiling: e.g. ordered candidate keyset + bounded batches + bulk qualified snapshot reads / indexes, or qualifying preselection / materialized read projection **only with version/currentness and equivalence proofs**. Preserve the accepted evaluator as semantic reference. A new cross-surface declarative field registry or generalized Search rewriter is **not** a preapproved solution.
- Each HTTP request has explicit finite server-side caps for candidate IDs fetched, SQL work, buffered match/evidence results, and defensible execution deadlines/cancellation behavior. **Do not claim a hard process-CPU-time bound that a synchronous Python/driver call cannot actually enforce:** specify enforceable page/scan/statement limits, PostgreSQL statement timeout, bounded external wait/admission and cancellation cleanup; measure worst-case CPU/memory and document any remaining non-preemptible operation as a retained #355 risk. Bound DB concurrency/admission as necessary for this Search path without implying all #355 connection/import hardening has been completed. No unbounded "keep fetching in a while loop until 20 matches" hidden inside one request. If a fixed scan budget expires, return PARTIAL + safe cursor or fail **visibly** if continuation cannot safely be issued.
- One HTTP evaluation must use consistent current evidence in each snapshot (including publisher and cross-Organization observation sets, current category, current revision, qualified design+variant and D29). Cross-request pagination **does not promise a persistent MVCC snapshot**. After revision, withdrawal, fresh publication or reconfirmation, later pages must revalidate current D29/claims and cannot leak stale positive eligibility. A deterministic restart/continuation policy must be documented and tested; old page membership is not promised to remain immutable while listings mutate.
- Search errors, DB failures, timeout/cancellation, malformed/expired tokens and missing data must remain distinguishable. Existing legacy unpaged persistence helpers and any non-public broker/private diagnostic consumers MUST be enumerated and preserved or migrated explicitly: SLICE-0092's accepted separate design-unresolved helper is not permission to silently overwrite legacy enumeration semantics. Public HTTP routes may not retain an unbounded compatibility escape hatch. A database error must not be converted to `INSUFFICIENT_DATA`, a fake empty COMPLETE page or successful 200. Repeated identical page requests over stable data must be reproducible; invalid/foreign/expired cursors must have zero mutations.

## 4. Truth/security invariants and exclusions

- All **11 accepted hard technical dimensions** stay unchanged (Sail 9 + Power 2); no paid-visibility relevance, new sort algorithm, additional filters or confidence score. Existing `CONFIRMED_MATCH`, `CONFIRMED_NON_MATCH`, `INSUFFICIENT_DATA` MUST/AND and distinct source states preserved. `PUBLISHER_CLAIM` is an issuer-qualified statement, NOT HullQ-independent design verification.
- Preserve D29 ACTIVE current public eligibility, freshness, existing discovery-token link provenance, ownership/cross-Organization privacy, no DRAFT or WITHDRAWN exposure, no owner-direct/trader authority bypass, no private source IDs in public JSON/URLs/logs.
- The newly accepted `MOTORSAILER` Sail-family placement is **decided but not yet runtime-implemented** under #372. This retrieval slice preserves the accepted *current* code exclusion until a separate, reviewed category admission change, not silently interpreting page enumeration as authorization to rewrite category truth.
- Existing broker-only authorized DRAFT Search-fit is not made public, paginated or semantically modified by this buyer-read capability.
- No cards, manufacturer/location/price/year filter family, broad SEO landing pages, production email/import feeds or real external inventory/pilot. M1a Buyer results presentation follows later. No new canonical technical-search criterion count.

## 5. Executable evidence and rejection rules

An independently reviewed SLICE-0096 implementation must retain:
1. A **deterministic synthetic fixture** representing matching results at the beginning/middle/end, many nonmatching candidates, zero-matches, source splits, missing/conflicting/current revision truth, Sail versus Power and category exclusion; use actual Alembic migrated PostgreSQL 18, actual API and Astro-built SSR.
2. Direct **unbounded reference versus all-page traversal equivalence** over stable small/medium fixtures for *every accepted technical query-family branch* (Sail pure draft, Sail mixed, Power drive-only, Power count-only and combined); verify exact matched IDs and classification/source basis, no duplicates, correct page order and no false final no-results state.
3. **Page-specific positive/negative proof:** page_size 1/20/50, invalid 0/51, empty and sparse pages with PARTIAL, final COMPLETE, invalid/stale/tampered/cross-category/query-cursor, duplicate/unknown params, canonical redirect and noindex behavior in five locales.
4. Two-connection/current-revision mutation proof: withdraw/reconfirm/category/claim changes between pages and within a page do not leak stale eligible positives or impossible cross-revision/variant conjunctions. Cancellation, timeout, malformed DB data and failure return typed visible errors; no silent page truncation.
5. **Measured boundedness and speed evidence**: compared counts and memory/elapsed distributions for both candidate planes, including mixed 0/40/200 and larger negative-heavy population if reproducible; record/justify exact per-request workload cap, improvement target from measured baseline and remaining limitations. A claim of “production-scale PASS” without hosted/real-load evidence is a reject.
6. Full existing Python/PG18/Web regressions, API and TypeScript response validator tests, repository readiness and exact-head CI/manufacturer + applicable deploy-build verification. Owner can run a retained synthetic local browser check and see truthful per-page state.

**Hard STOP:** If the implementer cannot provide a bounded correct continuation and keep the accepted truth/URL/DTO contracts consistent in one coherent vertical, report BLOCKED with measured counterexamples. Do NOT silently cap first N raw candidates, loosen match semantics, fabricate global counts, or mark #355 closed.

This contract may become controlling only when independently reviewed, accepted with the SLICE-0096 readiness package and merged. `PRODUCTION_READINESS_GATE_STATUS=IN_PROGRESS`, `PRODUCTION_LAUNCH_PACK_PHASE=NOT_STARTED`, #355 pre-external-data, #366 joint release and #372 Power/parity stay binding.
