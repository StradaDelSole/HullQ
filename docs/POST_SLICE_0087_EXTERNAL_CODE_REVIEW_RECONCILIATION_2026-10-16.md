## Answers to five open external-review questions

1. **Single-worker slow import: blocker?** **YES for first real external broker upload**, absent bounded concurrency/latency demonstration. `uvicorn` one API worker + blocking parse/DB on an async route can prevent *other API requests* from progressing. An exact duration is unknown without benchmark; require measured p95/p99 of upload/healthz/Search and memory/connection use under max-value and malicious fixtures. Synthetic local 0088 development remains allowed. See https://fastapi.tiangolo.com/async/ for native sync-path threadpool behavior.
2. **Does python-calamine enforce actual size or is compression ratio sufficient?** Not independently demonstrated by current source or the supplied review. Pin transitive calamine/zip crate version and test incorrect central-directory claims and actual worker RSS/CPU; ratio **alone is not enough** even for structurally valid ZIPs. Fail safely on resource overrun. A lower absolute threshold is a **hypothesis**, not a proven safe production bound.
3. **Can NautiX reject DOCTYPE?** `https://www.nautic-network.org/documentation` and pinned 1.4 XSD define `adverts.xml` without a DOCTYPE requirement. Strong DTD/DOCTYPE rejection is compatible with the documented standard subset; independently assert an exported canonical valid NautiX document without DTD passes schema/reader and malicious DTD is rejected. Avoid general claims about every possible vendor extension.
4. **Compose worker or host cron?** Operational choice open. Prefer a **version-controlled, monitored independent unit/timer** with explicit liveness/last-success/backlog/failure alerts, leases/retries and replay safety. Use Compose task if deployment/backup/observability proof fits, or versioned `systemd` timers if host-level supervision is accepted; **do not** assume running worker step or runbook means a deployed schedule. Notification delivery needs real accepted email provider separately; purge needs actual retention proof.
5. **Batch design/claim lookup and MVCC?** Feasible if the batch result is computed inside a transactionally coherent snapshot, such as `REPEATABLE READ READ ONLY` across all statements, or a proven single SQL statement (plus tests under concurrent claim updates). Simply issuing `= ANY(...)` for several ordinary `READ COMMITTED` queries can observe incompatible revisions. Cross-org conflicts and same-configuration AND must remain semantically identical.
