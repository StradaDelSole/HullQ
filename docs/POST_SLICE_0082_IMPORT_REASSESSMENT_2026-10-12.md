**Official NautiX sources reviewed (2026-10-12):**
- `https://nautix.nautic-network.org/`: NautiX v1.4, last modified **9 July 2026**; authoritative example XML and XSD at `https://nautix.nautic-network.org/v1.4/NautiX.xsd`.
- `https://www.nautic-network.org/documentation`: mandatory broker advert feed `adverts.xml`; `accounts.xml` optional for multi-provider marketplaces, `status.xml` still in development; per-advert ID/type/purpose/status/modified; empty values omitted; inactive adverts may omit content; boat/model/LOA, price/country, media semantics and v1.4 `validation=non-strict` checksum exception.
- `https://www.nautic-network.org/code-of-conduct`: **Nautic Network partner-to-partner data exchange is ongoing**, the code forbids chaining feeds and says partner exchange is not a one-time import. A broker **locally uploading an owned file** must not be represented as an approved NautiX Network partner exchange, and lawful access/rights/source provenance must be recorded. Do not implement network fetching/Push/partner publishing through a static-file parser.
- `https://www.boat24.ch/chen/dealers/infos/`: documented preference for NautiX feeds over legacy OpenMarine for automatic synchronization.
- `https://pypi.org/project/python-calamine/0.7.0/`: existing Python 3.14 wheel availability and a credible **single spreadsheet reader** for xls/xlsx/xlsb/ods; dependency safety/reproducibility to be verified in implementation, not asserted done by research.

**Reasoned format scope for ONE intake capability:** delimited `.csv`/`.tsv`, Excel `.xlsx`/`.xls`/`.xlsb`, OpenDocument `.ods`, JSON record arrays with documented profile, and NautiX **v1.4** `adverts.xml` via `.xml`; all feed one staging/validation/explicit-create-private-draft workflow. XML without an identified, supported NautiX namespace/schema is not universal; classify unsupported XML with actionable rejection. `.xlsm`/macro-enabled files, zip archives, PDFs, images, arbitrary web scraping, remote feed polling/Push, CRM-specific opaque formats and continuous sync are not presumed safely covered merely because an extension is familiar. Maintain an explicit supported-format registry and a provider-specific adapter seam rather than claim all future formats are implemented.
