# Security Findings Register — 2026-10 (SLICE-0078)

**Status:** RETAINED EVIDENCE

| ID | Severity | Finding | Evidence | Disposition |
|---|---|---|---|---|
| SEC-0078-01 | MEDIUM | `/api/auth/logout` had no CSRF discipline — a bare `<form>` POST from the browser straight to FastAPI could never carry one. `SameSite=Lax` already withholds the session cookie from a true cross-site POST in current browsers, so this was a defense-in-depth gap (consistency with every other mutating channel), not a demonstrated live bypass. | `SECURITY_ATTACK_SURFACE_MATRIX_2026-10.md` §4 | **FIXED.** Added `_require_logout_csrf` (exact-Origin + fixed `X-HullQ-Requested-With: broker-logout-v1` header) and an Astro same-origin proxy `web/src/pages/broker/logout.ts` so the browser's plain form POST goes through Astro's own server, which sets the header server-to-server. Retested: `test_logout_without_csrf_header_rejected` / `test_logout_with_correct_csrf_header_succeeds_and_clears_session` (backend) + `test_logout_without_csrf_header_is_rejected_and_session_survives` (`test_broker_workspace_access_api.py`) + 3 new `logoutProxy.test.ts` cases. |
| SEC-0078-02 | MEDIUM | No bounded abuse-rate protection existed on three highest-risk unbounded routes: anonymous buyer-contact (`/api/listings/{id}/contact` — Lead spam/enumeration), broker login-flow initiation (auth-flow abuse), and per-account media upload (storage-cost abuse). | `SECURITY_ATTACK_SURFACE_MATRIX_2026-10.md` §6 | **FIXED.** Added `hullq.security.rate_limit.FixedWindowRateLimiter` (in-process, per-`create_app()` instance — matches ADR-0010's single-VPS-process baseline, explicitly not distributed-accurate). Contact: 5/5min. Login: 20/5min. Media upload: 30/hour, keyed by account. Retested: 4 new adversarial tests + 6 unit tests, all passing; independence across categories explicitly proven. |
| SEC-0078-03 | MEDIUM | No baseline security response headers (`X-Content-Type-Options`, `X-Frame-Options`, CSP, `Permissions-Policy`) existed on FastAPI routes outside the handful of path-scoped header dicts (public listing, preview, owner-direct) — e.g. media-bytes, upload, lead-ops, draft, sale-outcome and performance routes returned none of these. | `SECURITY_ATTACK_SURFACE_MATRIX_2026-10.md` §8 | **FIXED.** Added `_BASELINE_SECURITY_RESPONSE_HEADERS`, merged into every response ahead of any path-scoped override (so existing per-route policy is preserved exactly, only the previously-absent baseline is added). HSTS is additionally asserted, but only once `_cookie_secure()` confirms the process is actually TLS-configured. Retested: 4 new adversarial tests. |
| SEC-0078-04 | MEDIUM | The Astro web package (`web/`) had no centralized security-header enforcement at all — each page set only its own `Cache-Control`/`X-Robots-Tag` individually, with nothing for CSP/`X-Frame-Options`/`X-Content-Type-Options`/`Permissions-Policy`/HSTS. | `SECURITY_ATTACK_SURFACE_MATRIX_2026-10.md` §8 | **FIXED.** Added `web/src/middleware.ts`, applied to every response without touching existing per-page `Cache-Control`/`X-Robots-Tag`. `script-src`/`style-src` allow `'unsafe-inline'` as a measured relaxation (every template renders user text only through Astro's auto-escaped `{expression}` syntax — confirmed no `set:html` anywhere in `web/src`); `object-src`/`frame-ancestors`/`base-uri` stay strict. Retested live: built production server, headers confirmed present on `/broker` and `/en/search` without disturbing those routes' own headers. No unit test (the virtual module `astro:middleware` is not resolvable under plain `node --test`; see adversarial evidence §3-4 for why and what substitutes for it). |
| SEC-0078-05 | — (test-fixture defect, not a product vulnerability) | Fixing SEC-0078-01 broke a pre-existing test (`test_broker_workspace_access_api.py::test_logout_clears_session`) because its `create_app()` fixture never configured `web_origin`/`HULLQ_WEB_ORIGIN`, which logout's new CSRF check now requires to resolve the accepted Origin. | `SECURITY_ADVERSARIAL_EVIDENCE_2026-10.md` §2 | **FIXED.** Passed `web_origin=_WEB_ORIGIN` into that file's shared `create_app()` call; updated the test to send the fixed CSRF header + Origin; added a companion negative-path test. Full file re-run: 14 passed. |
| SEC-0078-06 | — (test-coverage gap, not a product vulnerability) | The new `web/src/pages/broker/logout.ts` proxy had no test coverage, and its `brokerApi` import omitted the explicit `.ts` extension this repository's other proxy routes use for Node ESM resolution (tolerated by Astro/Vite's bundler, but not by plain `node --test`). | `SECURITY_ADVERSARIAL_EVIDENCE_2026-10.md` §3 | **FIXED.** Added the extension for convention-consistency (re-verified clean `astro check` + `npm run build`); added `web/src/lib/__tests__/logoutProxy.test.ts` (3 cases: header/Cookie/Origin forwarding + Set-Cookie relay, anonymous request, unreachable-upstream 502), mirroring `buyerLeadContactProxy.test.ts`'s existing pattern. |
| SEC-0078-08 | — (test-fixture defect, not a product vulnerability) | Remote CI's `db integration` job (full suite, real multi-process HTTP vertical proof) caught two more regressions the targeted local runs above did not reach: (a) `tests/persistence/test_public_listing_read_api.py::test_active_listing_response_has_noindex_header_and_no_preview_confidentiality` asserted `Referrer-Policy` was absent on the public listing route — true only because that header previously existed solely as part of the preview route's confidentiality headers (SLICE-0049 §12), now obsolete since SEC-0078-03 made it universal. (b) `scripts/inspect_broker_workspace_access.py` step 15 posted directly to `/api/auth/logout` with no CSRF header/Origin and no `HULLQ_WEB_ORIGIN` configured for its FastAPI subprocess — the same gap class as SEC-0078-05, in a real-process script this slice's pytest-focused regression sweep does not run. | CI run `37089927568` (first push) failure logs | **FIXED.** (a) Updated the assertion to expect `Referrer-Policy: no-referrer` (the new universal baseline) and added a dedicated baseline-headers test; `Cache-Control` absence (the real distinguishing preview-confidentiality signal) is unchanged. (b) Added `HULLQ_WEB_ORIGIN` to the script's FastAPI subprocess env, and changed the logout call to go through `{web_base}/broker/logout` (Astro's proxy) with an explicit `Origin` header, exactly mirroring real browser behavior now that logout requires it. Re-ran both locally: `test_public_listing_read_api.py` 12 passed; `inspect_broker_workspace_access.py` full proof -> PASS. Pushed as a follow-up commit for CI re-verification. |
| SEC-0078-07 | **HIGH (raw advisory) / assessed non-exploitable in HullQ's current reachable surface** | `npm audit` reports a HIGH-severity advisory (GHSA-ch52-4w7c-c8xp, CVSS 7.5, CWE-524 "cross-user cached response disclosure") against `http-cache-semantics`, pulled in transitively by `astro`. Confirmed via `npm view http-cache-semantics versions` and `npm view astro@<latest> dependencies.http-cache-semantics`: **no patched release exists at any published version** (the advisory's vulnerable range is `<=4.2.0`, which is the latest published version; `astro`'s latest release, `7.3.5`, still pins `^4.2.0`). The only call site in `astro`'s own source is `astro/dist/assets/build/remote.js` (`loadRemoteImage`/`revalidateRemoteImage`), exercised only by Astro's built-in remote-image optimization (`astro:assets`' `<Image>`/`getImage()` with a non-local `src`). Confirmed via repository-wide search: **`web/src` contains zero usage of `astro:assets`, `<Image>`, or `getImage()` with any source** — the vulnerable code path is present in the dependency tree but is dead/unreachable code for every HullQ request-handling path. | `SECURITY_ATTACK_SURFACE_MATRIX_2026-10.md` §9; `npm audit --audit-level=critical --json` output; `npm ls http-cache-semantics --all` (single path: `astro@7.3.1 → http-cache-semantics@4.2.0`) | **GENUINELY_OPEN — Project-Owner risk-acceptance required before this item can be marked PASS/closed.** No in-slice fix exists (no patched dependency to upgrade to, and removing/vendoring Astro's asset pipeline is out of this slice's scope and disproportionate to an unreachable code path). Compensating action taken this slice: the newly added CI step (`.github/workflows/ci.yml`, "Audit web dependencies") is set to `npm audit --audit-level=critical` rather than `high` specifically so it does not permanently fail CI on this one documented, unreachable, unfixable advisory, while still failing on any Critical finding or a new High this reasoning does not cover. This finding must be re-reviewed (a) the moment a patched `http-cache-semantics`/`astro` release exists, or (b) if `web/src` ever adds any remote-image `astro:assets` usage, at which point reachability changes and this disposition no longer holds. |
