| SEC-0078-09 | **HIGH** | Independent review of the SLICE-0078 candidate found that `FixedWindowRateLimiter` (introduced by this same slice as SEC-0078-02's fix) retained one `dict` entry per distinct key forever — a key was only reset/reclaimed if *that same key* was observed again after its window expired. `_client_rate_limit_key` keys the contact and login limiters on `request.client.host` (the raw TCP peer address) with **no authentication required** on either route. An attacker needs no botnet to generate effectively unbounded distinct keys against this exposed surface: a single host with a routed IPv6 prefix (a `/64` or `/56` allocation is standard from most cloud/VPS providers, including HullQ's own ADR-0010 VPS baseline) can bind from billions of distinct source addresses without any sustained per-address cost. Each entry is small, but unbounded growth against the single application process ADR-0010 specifies (no distributed/multi-instance deployment) is a real memory-exhaustion/availability threat against the whole product, reachable by one unauthenticated remote actor — classified HIGH (CWE-770, unauthenticated/remotely-reachable resource exhaustion), not merely a hygiene concern, precisely because the mitigation *for* unbounded abuse must not itself become a new unbounded-resource vector. | Independent review finding A; `src/hullq/security/rate_limit.py` (pre-fix) | **FIXED.** `FixedWindowRateLimiter` now retains at most `max_keys` entries (default `10_000`) via an LRU-ordered `OrderedDict`: every `allow()` call first reclaims every entry whose window has fully lapsed (cheap/amortized — expired/inactive keys are, by construction, the least-recently-touched ones), and only evicts the single coldest entry if a genuinely new key still can't fit after reclaiming. An actively-reused key is always most-recently-touched and therefore never the eviction target, so legitimate rate-limiting accuracy is preserved under normal load; under sustained adversarial cardinality pressure the bound is enforced by sacrificing perfect per-key accounting (a rare forced reset) rather than ever exceeding `max_keys` retained entries — exactly the required fail-safe direction. Retested: `tests/unit/test_rate_limit_unit.py::TestBoundedRetainedState` (5 new tests: ordinary counting unchanged, expired-key reclaim, hard-cap-under-unique-key-flood, active-key-survives-eviction-pressure, category-independence-preserved) plus the full existing `TestRateLimitingAdversarial` suite (4 tests) re-run clean against the new implementation. |
