## 3. Result-state matrix

| Scenario | Design-linked result | Claim-only result |
|---|---|---|
| Publisher-owned explicit `POWER` + matching token claim | `CONFIRMED_MATCH` (requires design-side match too) | `CONFIRMED_MATCH` |
| Explicit `SAIL`/`MOTORSAILER`/cross-Org `CONFLICT` category | `CONFIRMED_NON_MATCH` (`category_exclusion` populated) | `CONFIRMED_NON_MATCH` (`category_exclusion` populated) |
| Missing/`UNKNOWN` category, or `POWER` asserted only by a different Organization | `INSUFFICIENT_DATA` | `INSUFFICIENT_DATA` |
| Category admitted, but drive is `OTHER`/`UNKNOWN`/wrong single token | `CONFIRMED_NON_MATCH` | `CONFIRMED_NON_MATCH` |
| Category admitted, publisher's own drive is `MIXED`, uncontested by any other current claiming Organization (review amendment Finding A, re-homed by Finding H) | `INSUFFICIENT_DATA` for every one of the five tokens — `MIXED` never proves the absence of any single accepted drive. Applied as a **result-level** downgrade (`hullq.application.power_inventory_query._downgrade_mixed_non_match_to_insufficient_data`) strictly after ordinary qualification, not at the claim-read boundary — see Finding H below | `INSUFFICIENT_DATA` for every one of the five tokens, identical reasoning |
| Cross-Organization conflicting current drive values (same PhysicalBoat, same POWER category) — including a single-token publisher claim contested by another Organization's current `MIXED` claim, either direction (review amendment Finding H) | `INSUFFICIENT_DATA` for every disputed token — same-PhysicalBoat cross-Organization contradiction guard (`_qualify_claim_field`), now applied against the TRUE, unmasked claim values | `INSUFFICIENT_DATA`, identical reasoning |
| BoatDesign `drive_type` is `saildrive`/`other`/`unknown` (design-linked only) | `INSUFFICIENT_DATA` at the design level (never promoted to a concrete check) | N/A |
| D29-suppressed (withdrawn/non-public/stale) | excluded from every result surface | excluded from every result surface |

**`OTHER` vs `MIXED` (review amendment Finding A, re-homed by Finding H, resolved):** `OTHER` denotes a confirmed single (if uncatalogued) drive — the publisher would have used the real token if the boat had one of the five, so `OTHER` genuinely is not any of them; ordinary categorical equality already yields the correct `CONFIRMED_NON_MATCH`, identical treatment to `HullMaterial.OTHER`/`KeelConfiguration.OTHER` elsewhere in this codebase. `MIXED` denotes unlike drive types that may include one of the five accepted tokens (contract: "even if the vessel uses one of the types"), so it can never be read as a proven exclusion for the publisher's own uncontested claim — but it is a plain, unmasked passthrough value at the claim-read boundary (`hullq.search.power_criteria_registry._read_power_drive_configuration_claim`), exactly like every other value. "Not a confirmed exclusion" is applied only afterward, as a result-level downgrade restricted to the publisher's own uncontested `CONFIRMED_NON_MATCH` outcome (`hullq.application.power_inventory_query._downgrade_mixed_non_match_to_insufficient_data`) — never by hiding another Organization's current `MIXED` claim from the ordinary cross-Organization contradiction guard. See Finding H (§7) for why the earlier claim-read-level masking was wrong.

## 4. NautiX export guard (review amendment Finding B, resolved)

`hullq.application.inventory_export._claim_physical_boat_facts` now populates `ExportRow.vessel_category` from the **resolved** current category (`hullq.domain.vessel_category.resolve_vessel_category`: design plane + this Organization's own claim + every other current claiming Organization) rather than only the exporting Organization's own raw claim. `hullq.domain.inventory_export._nautix_preflight` rejects the row closed whenever the resolved state is explicitly `POWER`/`MOTORSAILER`/`CONFLICT` (`_NAUTIX_EXCLUDED_VESSEL_CATEGORIES`); `None`/`SAIL`/`UNKNOWN` all preserve the pre-0093 default-SAIL NautiX assumption unchanged. Proven with real PostgreSQL 18 (`tests/persistence/test_inventory_export_category_slice_0093.py`, 6 tests): a design-only-POWER BoatDesign with no publisher category claim at all now fails closed (the exact gap the review named — the pre-amendment guard, reading only the publisher's own claim, would have let this row through as a default `sail-yacht`); a publisher-SAIL-vs-design-POWER disagreement resolves to `CONFLICT` and also fails closed; ordinary agreeing SAIL and legacy no-category-evidence listings keep exporting unchanged; the other six accepted formats are never affected.

## 7. Review amendment Round 2 (Findings G–K, resolved)

**G (BLOCKER) — design-linked category/drive MVCC coherence.** The design-linked funnel previously resolved category (`resolve_physical_boat_vessel_category`, one statement) and then separately classified the concrete drive (`classify_concrete_candidate`'s own fresh `list_current_physical_boat_claim_observations` call, a second, independently-timed statement) — reopening, for the Power-specific drive field, exactly the two-statement MVCC tear window SLICE-0091 amendment Finding F had already closed for category-alone. A concurrent revision landing between those two statements could combine a pre-commit category with a post-commit drive (or vice versa) and produce a false `CONFIRMED_MATCH`.

  Fixed by a new combined single-statement snapshot, `hullq.persistence.power_category_drive_snapshot.fetch_power_category_drive_snapshot` — the same `vessel_category_snapshot.py` design-CTE/concrete-CTE/`to_jsonb`/`jsonb_agg` discipline, extended so the concrete CTE also projects the `power_drive_configuration_*` columns. `classify_concrete_candidate` (`hullq.application.native_inventory_query`) gained an optional `observations` parameter — `None` (every existing Sail call site, unchanged behavior) fetches fresh; the design-linked Power path now passes the combined snapshot's own observations, so category resolution and drive classification are always read from the identical PostgreSQL statement/snapshot. Proven by a new true two-connection concurrency test, `test_design_linked_two_connection_concurrent_revision_never_sees_hybrid_state` (`tests/persistence/test_power_inventory_query_slice_0093.py`): a writer holds a new revision (SAIL category + POD drive) open on one connection while a separate reader connection evaluates Search on the other — the reader sees only the old, fully-committed revision (POWER + SHAFT) for *both* fields, never a torn combination; after commit the new revision is visible atomically.

**H (BLOCKER) — cross-Organization `MIXED` visibility.** The Round 1 fix for Finding A reinterpreted every current `VALUE_ASSERTION(MIXED)` claim as `UNKNOWN` at the shared per-observation read boundary (`hullq.search.power_criteria_registry._read_power_drive_configuration_claim`) — applied uniformly to the publisher's own claim **and** every other current claiming Organization's claim, since `_qualify_claims_against_definitions` builds its cross-Organization contradiction set from that same accessor. That silently erased another Organization's current contradictory `MIXED` claim from the ordinary same-PhysicalBoat contradiction guard.

  Fixed by reverting `_read_power_drive_configuration_claim` to a plain passthrough (identical shape to every other Sail `_read_*_claim` accessor) and moving "a current `MIXED` claim is never a confirmed exclusion" to a result-level downgrade, `hullq.application.power_inventory_query._downgrade_mixed_non_match_to_insufficient_data`, applied only after ordinary qualification has already run — so it only ever fires on the publisher's own uncontested `CONFIRMED_NON_MATCH`. Proven with real PostgreSQL 18 (`tests/persistence/test_power_inventory_query_slice_0093.py`): publisher `SHAFT` vs. another Organization's current `MIXED` fails closed to `INSUFFICIENT_DATA` (`test_publisher_shaft_versus_other_organization_mixed_fails_closed`); the reverse, publisher `MIXED` vs. another Organization's `SHAFT`, also fails closed (`test_publisher_mixed_versus_other_organization_shaft_fails_closed`); a publisher-only `MIXED` claim with no other Organization at all keeps the ordinary Finding A downgrade (`test_publisher_mixed_with_no_other_organization_is_still_insufficient_not_excluded`); and two Organizations agreeing on the identical single token still confirm (`test_publisher_shaft_versus_other_organization_shaft_is_a_nonconflicting_confirmed_match`).

**I (HIGH) — retained inspector repair.** The inspector's editor pre-fill check (step 13) computed `prefilled_ok` but never folded it into the aggregate `ok` flag, so its failure could never flip the overall exit code; the check itself also only tested that `value="POD"` and the bare word `"selected"` both appeared *somewhere* in the whole claim-editor form block, not that the `power_drive_configuration_value` select's own POD `<option>` specifically carried `selected`. Fixed: `ok &= prefilled_ok` now gates the aggregate result, and new `_select_block`/`_option_is_selected` helpers scope the check to the exact `<select name="power_drive_configuration_value">` element and assert POD (and *only* POD) carries the `selected` attribute. The five-locale buyer check (step 6) now also asserts `<meta name="robots" content="noindex">` and the exact locale-specific `t.publisherClaimDisclaimer` substring (`web/src/lib/powerSearchText.ts`) in every one of the five built SSR locales, not only that the claim-only match renders. Re-run against real PostgreSQL 18 + FastAPI + built Astro SSR: all 17 steps genuinely `OK` (`SLICE-0093 POWER DRIVE CONFIGURATION SEARCH + EDITOR PROOF RESULT -> PASS`).

**J (MEDIUM) — Power response validator hardening.** `validatePowerSearchResultBody` (`web/src/lib/powerSearchApi.ts`) now takes an `expected: { locale, powerDrive }` parameter and rejects: a response for a different locale than requested; a filtered request silently served a no-op BASE response; a RESULT response echoing back a `power_drive` token other than the one actually requested; an unfiltered request served an active RESULT; a BASE body carrying non-empty match arrays or positive counts (contradictory BASE); and any malformed nested `criterion_evidence`/`design_configuration_evidence`/`design_evaluation` object (new `isValidCriterionEvidence`/`isValidConfigurationEvidence`/`isValidDesignEvaluation` deep validators, not only `Array.isArray(...)` on the enclosing array). `fetchPowerSearch` now computes `expected` from the real requested locale/query string before validating. Proven by `web/src/lib/__tests__/powerSearchApi.test.ts` (both direct `validatePowerSearchResultBody` unit cases and real-HTTP `fetchPowerSearch` stub-server cases for every one of the above) and `astro check` (0 errors).

**K (MEDIUM) — real PostgreSQL 18 EXPLAIN evidence.** `tests/persistence/test_power_inventory_query_performance_slice_0093.py` gained two new tests that capture the exact `(sql, params)` the real evaluation path issues (never a hand-copied SQL literal) and replay it as `EXPLAIN (ANALYZE, BUFFERS)` on the same seeded connection/schema: the claim-only plane's batched observations statement at 200 candidates, and one of the design-linked plane's per-candidate combined category+drive snapshot statements at 10 candidates. Both plans use index scans for the point lookups (`boat_design_category_assertion_heads_pkey`, `pk_pb_claim_heads`) at this bounded synthetic scale; no index-selectivity claim is made for a production-scale `physical_boat_claim_revisions` table, and issue #355's pre-real-data/pilot production-scale STOP remains explicitly **OPEN** regardless of these measurements — this is one honest representative data point, never a capacity guarantee.

## 8. Explicit limitations (never silently claimed complete)

- `STERNDRIVE`/`POD`/`WATERJET` have **no design-linked bridge** in this slice: a design-linked PhysicalBoat can never reach `CONFIRMED_MATCH` for those three tokens, only `INSUFFICIENT_DATA` at the design level; they are reachable only through the design-unresolved claim-only path. This is a genuine, deliberate coverage gap (contract: "No v0.7 BoatDesign schema/migration is granted by this criterion"), not an oversight.
- Only one Power criterion exists; engine count/make/model, horsepower, fuel/energy source, speed/range/operating-point, and Power Broker Search-fit remain out of scope (tracked under #372).
- The design-linked plane's per-candidate (O(N)) cost is measured and documented (§5) but not newly optimized in this amendment; the pre-real-data/pilot scaling STOP (#355) is unchanged and still open.
- No real brokers, owner-direct trust, public pilot, or SEO/indexable exposure is introduced; both the API route and the five Astro pages are noindex.
- The retained inspector (`scripts/inspect_slice_0093_power_drive_search.py`) uses `urllib` plus a standards-compliant cookie jar for real HTTP/form-POST evidence against a real local OIDC test issuer, FastAPI backend and built Astro/Node SSR server — this is HTTP-level automation, explicitly not a genuine browser (no JS execution, no DOM rendering, no Playwright/Selenium-style page automation).
