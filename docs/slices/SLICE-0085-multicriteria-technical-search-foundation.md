## Normative bounded first-bundle semantics

### LOA — one additional public Search dimension

- Canonical keys: `loa_min` and `loa_max`, positive finite plain-decimal **metres**, compatible with the accepted draft maximum lexical grammar (ASCII digits and optional full fractional part, no sign, exponent, comma, whitespace, empty or float intermediate). Canonicalize with one shared exact Decimal formatter; no implicit epsilon or floating point tolerance. Each key may appear at most once; repeated equal values redirect only if the backend existing canonical-URL duplicate rule safely applies, conflicting values always INVALID. Require `loa_min <= loa_max` whenever both supplied; inclusive ends. Reject unreasonable resource-length input before Decimal conversion (actual explicit implementation cap to be justified in tests).
- LOA alone may be min, max or inclusive range; this is **ONE** distinct dimension in criteria count. Mixed `draft_max`, `keel_configuration`, `rudder_configuration` and LOA min/max use one global hard AND over the SAME resolved configuration. If both LOA bounds exist they generate two numeric leaves against one qualified `loa_m` projection; deduplicate this projection spec safely, retaining both requested comparisons and their evidence.
- Design/NamedVariant exact qualified pointers: `/baseline/dimensions/loa_m`, `/overrides/dimensions/loa_m` in both accepted schema versions, with inherited values following accepted variant qualification rules. No inferred length from another dimension or marketing text.
- Concrete truth: the publisher's currently asserted `physical_boat.loa_length` `VALUE_ASSERTION(Decimal metres)` must independently satisfy each bound; absent/UNKNOWN => insufficient data. Competing current other-Organization claims with different concrete LOA values => conflicting UNKNOWN using the already accepted same-boat observation rules. Design truth alone NEVER confirms an actual offered boat.
- Public canonical key order is the accepted lexicographic policy, not UI display order: `draft_max`, `keel_configuration`, `loa_max`, `loa_min`, `rudder_configuration` for supported present keys. Server owns validation, ordering and redirects; frontend does not infer canonical URL by alternative rules.

### Rudder/skeg — additional bounded categorical public Search dimension

**One public parameter `rudder_configuration`** initially admits only these existing concrete claim tokens when its design meaning can be proven from generation-aware, qualified data: `SKEG_HUNG`, `TRANSOM_HUNG`, `SPADE`, `TWIN`. `OTHER` is an existing claim token but is NOT a verified search category. A value missing an independently qualified design-to-concrete association never counts as a public confirmed match.

**Conservative, auditable source mapping rules (do not invent a flattened rudder truth from v0.6):**
- For a genuine v0.5 BoatDesign, qualify `baseline.configuration.rudder_type` or its NamedVariant `overrides.configuration.rudder_type` using the exact generation-specific persisted FieldResolution subject/pointer; `skeg_hung` and `partial_skeg` may support `SKEG_HUNG` (both definitionally skeg-supported), `transom_hung` → `TRANSOM_HUNG`, `spade` → `SPADE`, and `twin` → `TWIN` **only if conflicting count evidence is absent**. `keel_hung`, `other`, `unknown` do not map to an invented accepted category.
- For a genuine v0.6 BoatDesign, each contributing `appendages` field must be **separately qualified** at the right baseline/variant pointer. `rudder_support=skeg` can support `SKEG_HUNG`; `rudder_position=transom` **and** `rudder_support=transom` can support `TRANSOM_HUNG`; `rudder_count=2` can support `TWIN` only where other qualified records do not conflict. `rudder_support=free` **does not prove** `SPADE`; no other bare property automatically proves that compound label. `rudder_balance` is independent and MUST NOT be inferred. Any unresolved overlap between multiple possible coarse enum labels, incompatible source details or uncertain variant applicability → `INSUFFICIENT_DATA` for that flattened category instead of guessing one.
- Reuse the accepted version mapping conservativity from `docs/engineering/BOAT_DESIGN_V05_TO_V06_MAPPING.md`; it is NOT approval for a runtime v0.5→v0.6 migration. No false negative is turned into a confirmed positive from an absent field. All concrete matching still requires the exact current publisher `physical_boat.rudder_configuration` VALUE_ASSERTION and cross-Organization agreement. Flat claim can underrepresent legitimate orthogonal v0.6 facts; show unsupported/insufficient honestly. Never infer one of these concrete claims from BoatDesign structure alone.
- If a specific enum value cannot be implemented with reliable generation/FieldResolution and real E2E evidence, it MUST be **removed from the supported public vocabulary in the final reviewed code** and reported transparently as an owner-visible accepted scope limitation; at least `SKEG_HUNG` must be demonstrated in real synthetic public Search and broker Search-fit for rudder to count as implemented. If not even that is provable, STOP with evidence and request Owner scope adjustment: a registry-only slice plus LOA is not the accepted first bundle.

### `LONG_KEEL` — conservative amendment to criterion #2, not a new dimension

- Proposed admitted request token `LONG_KEEL` exists in the accepted concrete `physical_boat.keel_configuration` enum but not current accepted public Search vocabulary. It may be added **only** on qualified exact baseline/NamedVariant BoatDesign `keel_type=full` in generation-appropriate `configuration.keel_type` (v0.5) or `appendages.keel_type` (v0.6), with the publisher's independent exact `LONG_KEEL` concrete claim and no same-boat conflicting other-Org claims. `full` represents the undivided full-length keel category; never extend this decision to `modified_full`, `long_fin`, `shoal`, `bilge`, `other` or any partial support merely by lexical resemblance.
- Before public enabling, explicit focused independent reviewer sign-off is required for the conservative `full`↔`LONG_KEEL` meaning, generation-specific version pointers and the fail-closed variant/claim truth. If this cannot be substantiated from the accepted taxonomy and executable E2E proof, **leave `LONG_KEEL` publicly unsupported and report it as a documented Owner decision blocker**, never silently mark it implemented. Existing six accepted keel values remain unchanged.
- The `LONG_KEEL` amendment does **not** increment `TECHNICAL_NATIVE_SEARCH_CRITERIA_COUNT`.
